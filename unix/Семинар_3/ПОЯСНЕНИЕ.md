# Пояснение к защите: сервер и клиенты на FIFO

## Что реализовано

Работа состоит из двух программ.

- `server` создаёт один известный всем клиентам именованный канал — серверный FIFO.
- `client` создаёт свой уникальный FIFO и передаёт серверу полный путь к нему.
- Сервер после каждого запроса делает `fork()`. Родитель продолжает принимать новых клиентов, а дочерний процесс передаёт символы только этому клиенту.
- Клиент читает поток 30 секунд, считает байты (каждый переданный символ — один байт), затем удаляет свой FIFO.

Таким образом, выполнены все пункты задания, включая одновременную работу нескольких клиентов.

## Схема взаимодействия

```text
client 1 -- путь к /tmp/fifo_client_101 --> серверный FIFO --> родитель server
                                                            |
                                                          fork()
                                                            |
client 1 <-- случайные символы <-------------------- дочерний server

client 2 -- путь к /tmp/fifo_client_102 --> серверный FIFO --> родитель server
                                                            |
                                                          fork()
                                                            |
client 2 <-- случайные символы <-------------------- другой дочерний server
```

Серверный FIFO нужен только для подключения. Для передачи данных каждому клиенту используется отдельный канал клиента. Поэтому данные разных клиентов не смешиваются.

## `server.c`

### Подготовка и создание канала

В `main()` выбирается путь FIFO: первый аргумент командной строки либо `/tmp/fifo_server` по умолчанию.

```c
umask(0);
mkfifo(server_fifo, 0666);
```

`mkfifo()` создаёт именованный канал в файловой системе. `umask(0)` временно отменяет маску прав, чтобы права `0666` не были урезаны системной маской. Ошибка `EEXIST` не является критичной: это значит, что FIFO уже существует.

Сервер открывает свой FIFO с `O_RDWR`, а не только `O_RDONLY`. Его собственный дескриптор на запись не даёт `read()` вернуть конец файла, когда в данный момент нет подключённых клиентов. Поэтому сервер продолжает ожидать следующие подключения.

### Приём запроса

Клиент отправляет в серверный FIFO строку:

```text
/tmp/fifo_client_12345\n
```

Сервер читает данные в `buffer`, собирает символы до `\n` в `pending`, затем получает законченное имя клиентского FIFO. Нужен такой разбор, потому что `read()` не обязан вернуть ровно одну строку: одна запись может прийти частями, либо одно чтение может содержать несколько запросов.

Запрос короткий и меньше `PIPE_BUF`. Запись пути одним сообщением атомарна для FIFO, поэтому сообщения одновременно подключающихся клиентов не перемешиваются.

### Создание обработчика клиента

После получения пути выполняется:

```c
child = fork();
if (child == 0)
    serve_client(pending);
```

`fork()` создаёт копию процесса.

- В родителе `child` содержит PID ребёнка. Родитель сразу возвращается к `read()` и готов принимать другого клиента.
- У ребёнка `child == 0`; он вызывает `serve_client()` и занимается только одним клиентом.

`signal(SIGCHLD, SIG_IGN)` не даёт завершившимся детям оставаться процессами-«зомби».

### Передача данных и приоритет

В `serve_client()` ребёнок открывает FIFO конкретного клиента в режиме `O_WRONLY`. Открытие ожидает, пока клиент не откроет тот же FIFO для чтения — так обеспечивается синхронизация.

В бесконечном цикле выбирается буква от `A` до `Z` и записывается в канал. После каждой тысячи символов с вероятностью примерно 19% вызывается:

```c
setpriority(PRIO_PROCESS, getpid(), rand_r(&seed) % 11);
```

`PRIO_PROCESS` означает, что меняется приоритет процесса, `getpid()` — PID именно дочернего процесса, а `rand_r(...) % 11` даёт значение от 0 до 10. Следовательно, приоритет меняется независимо для каждого клиента.

На некоторых системах обычный пользователь может повышать значение nice (делать процесс менее приоритетным), но не может вернуть его к меньшему значению без специальных прав. Поэтому неудачный случайный вызов намеренно не останавливает передачу: это ограничение прав ОС, а не ошибка протокола.

Когда клиент закрывает FIFO, запись `write()` завершается ошибкой (`EPIPE`), дочерний процесс выходит из цикла, закрывает дескриптор и завершается. `write_all()` полезна в общем случае: она гарантирует запись всех переданных байтов, даже если системный вызов записал только часть буфера.

### Завершение сервера

Обработчик `stop_server()` вызывается по `Ctrl+C` (`SIGINT`) или `SIGTERM`, удаляет серверный FIFO через `unlink()` и завершает сервер. FIFO не исчезает сам после завершения процесса, поэтому `unlink()` необходим.

## `client.c`

### Создание личного FIFO и подключение

Клиент формирует уникальное имя:

```c
/tmp/fifo_client_<PID>
```

PID процесса уникален среди одновременно работающих процессов, поэтому несколько клиентов не создадут один и тот же FIFO. Затем клиент вызывает `mkfifo()`.

Далее клиент открывает известный серверный FIFO в режиме `O_WRONLY` и передаёт в него путь своего FIFO, заканчивая его символом новой строки. После отправки дескриптор серверного FIFO больше не нужен и закрывается.

Затем клиент открывает свой FIFO с `O_RDONLY`. Это разблокирует дочерний процесс сервера, который ждал возможности открыть этот же FIFO для записи.

### Подсчёт за 30 секунд

Перед чтением сохраняется точка времени `started` с помощью `clock_gettime(CLOCK_MONOTONIC, ...)`. Используются монотонные часы: изменение системного времени пользователем или NTP не исказит интервал.

Каждый успешный `read()` возвращает число полученных байтов. Оно добавляется к `symbols`. Поскольку сервер отправляет по одному символу, это и есть число принятых символов.

После чтения сравнивается время с `started`. Как только прошло 30 секунд, цикл заканчивается. Клиент закрывает дескриптор и делает `unlink(client_fifo)`. Закрытие сообщает серверному ребёнку, что передача больше не нужна.

`SIGINT` и `SIGTERM` также приводят к штатному завершению клиента: канал и файл FIFO будут закрыты и удалены.

## `Makefile`

- `make` или `make all` собирает `server` и `client` компилятором `cc`.
- `make clean` удаляет только собранные исполняемые файлы.
- Флаги `-Wall -Wextra -Wpedantic` включают дополнительные предупреждения компилятора.

## Вопросы, которые могут задать

**Почему нельзя передавать всем клиентам данные через один серверный FIFO?**  Читатели конкурируют за байты: неизвестно, какой клиент прочитает конкретное сообщение. Личный FIFO позволяет однозначно направить поток нужному клиенту.

**Почему используется `fork()`?**  Обработчик одного клиента бесконечно пишет символы и не должен блокировать сервер. Отдельный дочерний процесс позволяет родителю сразу принять следующего клиента.

**Чем FIFO отличается от обычного файла?**  FIFO имеет имя в файловой системе, но данные не хранятся на диске: они передаются через буфер ядра между процессами. После чтения байты исчезают.

**Зачем `unlink()`?**  Закрытие дескриптора освобождает ресурс процесса, но имя FIFO остаётся в файловой системе. `unlink()` удаляет это имя.

**Что произойдёт при одновременном подключении клиентов?**  Пути записываются в серверный FIFO атомарно, сервер по очереди извлекает их и для каждого создаёт отдельного потомка. Передача идёт параллельно в независимых FIFO.

**Почему сервер открыт как `O_RDWR`?**  Без собственного конца записи сервер при отсутствии клиентов получил бы EOF из `read()`. `O_RDWR` удерживает канал открытым и позволяет бесконечно ждать новые подключения.
