# Лабораторная 5. Планировщик событий MySQL

События автоматизируют три операции в базе квартплаты: пересчёт помесячных итогов, перенос старых платежей в архив и удаление просроченных объявлений. У планировщика нет истории запусков, только поле `LAST_EXECUTED`, поэтому каждый запуск пишет строку в таблицу `event_log`.

## Запуск

```bash
docker compose up -d          # из папки lab_5
docker exec -i lab5_db mysql --default-character-set=utf8mb4 -uroot -proot -t < sql/03_demo.sql
```

| Что | Адрес |
|---|---|
| MySQL | `localhost:3309`, пользователь `root` / `root`, БД `kvartplata` |
| phpMyAdmin | http://localhost:8082 |

Сервер стартует с `--event-scheduler=OFF`. Включение — первая команда сценария. Повторный прогон с чистыми данными: `docker compose down -v && docker compose up -d`.

Протокол уже выполненного прогона: `results/demo_output.txt`.

## Пункты задания

| Пункт | Где |
|---|---|
| 1. Проверить и включить планировщик | `SET GLOBAL event_scheduler = ON` в `sql/03_demo.sql` |
| 2. Событие для периодического запроса | `ev_refresh_summary`, `ev_purge_notices` |
| 3. Однократное и повторяющееся расписание | `ev_archive_old_payments` — `AT` через 5 секунд; два других — `EVERY 10 SECOND`, затем пересчёт переведён на `EVERY 1 MONTH` |
| 4. Журнал и статус | таблица `event_log` и `information_schema.EVENTS` (`STATUS`, `LAST_EXECUTED`) |
| 5. Практический сценарий | процедуры `sp_refresh_summary`, `sp_archive_payments`, `sp_purge_notices` |
| 6. Отключить и удалить | `ALTER EVENT ... DISABLE`, затем `DROP EVENT` |

## События

Тело каждого события — один `CALL`. Так определение целиком видно в `information_schema.EVENTS`.

| Событие | Расписание на время проверки | Что делает |
|---|---|---|
| `ev_refresh_summary` | каждые 10 секунд, затем 1-го числа в 00:05 | заново заполняет `monthly_summary`: начислено, оплачено, сальдо на конец месяца |
| `ev_archive_old_payments` | один раз, через 5 секунд | платежи раньше `2024-01-01` копирует в `payments_archive` и удаляет из `payments` |
| `ev_purge_notices` | каждые 10 секунд | удаляет объявления с `expires_at` в прошлом |

Десять секунд вместо месяца нужны только чтобы дождаться запусков в этом сценарии. После проверки пересчёт итогов переводится на ежемесячное расписание, очистка отключается, затем все три события удаляются.

## Результат прогона

Планировщик перешёл из `OFF` в `ON`. За 25 секунд журнал зафиксировал:

| Событие | Запусков | Что изменилось |
|---|---|---|
| `ev_archive_old_payments` | 1 | 2 платежа (50 ₽ от 2022-03-01 и 80 ₽ от 2021-12-15) ушли в архив. Статус события стал `DISABLED` — однократное уже отработало |
| `ev_purge_notices` | 3 | первый запуск удалил 2 просроченных объявления, дальше удалять было нечего. Осталось объявление со сроком до 2030-12-31 |
| `ev_refresh_summary` | 3 | каждый раз 6 строк итогов. Сальдо совпало с ручным расчётом по всем квартирам |

Сальдо на конец месяца = сальдо на начало сентября + начисления − платежи.

| Кв. | Сентябрь | Октябрь |
|---|---|---|
| 1 | 1000 + 500 − 0 = 1500 | 1500 + 400 − 300 = 1600 |
| 2 | 200 + 300 − 300 = 200 | 200 + 300 − 0 = 500 |
| 3 | 0 + 150 − 0 = 150 | 150 + 150 − 100 = 200 |

После `DROP EVENT` в `information_schema.EVENTS` не осталось ни одного события этой базы. Архив, итоги, уцелевшее объявление и журнал остались: по ним видно, что события успели сделать до удаления.
